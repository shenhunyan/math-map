# Contributing

The most valuable thing you can do here is **disagree with the structure**.

Definitions and visuals can be improved incrementally, but a wrong prerequisite edge quietly poisons everything downstream — the diagnostic engine, the learning paths, and every student who gets sent back to the wrong chapter.

---

## The three kinds of contribution, ranked by value

### 1. Fix a prerequisite edge ← highest value

Every cell has a `pre` array: the cells that must come before it.

```json
{
  "id": "j_quad",
  "name": "一元二次方程 / Quadratic equations",
  "pre": ["s_letter", "j_real"],
  "note": "解析式 × 等式变形"
}
```

If you think an edge is wrong, open an issue with this format:

> **Edge**: `j_sys → j_func`
> **Claim**: this is reversed in Chinese textbooks. Systems of two linear equations are taught in Grade 7, linear functions in Grade 8.
> **Evidence**: 人教版七年级下册 §8, 八年级下册 §19.

That's it. Evidence from an actual syllabus settles it faster than any argument.

**Three edges have already been reversed or removed this way.** It is not a theoretical request.

### 2. Add a cell for upper-division or graduate mathematics

The map currently stops at undergraduate. Differential geometry, algebraic topology,
commutative algebra, representation theory, measure theory are all thin or missing.

A cell needs five fields:

| Field | What goes in it | Standard |
|---|---|---|
| `name` | 中文名 / English name | Use the term from a standard textbook, not a paraphrase |
| `pre` | ids of prerequisite cells | Ask: *can a student learn this without that?* If yes, don't add the edge |
| `items` | 4–7 knowledge points, in teaching order | These become diagnostic questions. Each must be testable in one question |
| `def` | 60–120 字 strict definition | No analogies. No "就像". A definition, not a description |
| `src` | 2 real textbooks + chapter | Must actually exist at that chapter. Do not guess |

### 3. Translate

The interface and all definitions are in Chinese. An English layer would open the
whole thing to a much larger audience. This is a large but highly parallel task —
translate one cell at a time, open a PR per batch.

---

## What is *not* wanted

- **More cells for the sake of count.** 166 is enough to make the point. A padded cell is worse than an empty one.
- **Speculative edges** ("these feel related"). Every edge must survive the question *can B be learned without A?*
- **Reformatting PRs.** The files are hand-written single-file HTML on purpose. Running a formatter over them creates diffs nobody can review.

## How to actually submit

Right now the authoritative data lives inside `math-map.html` (the `CUR` and
`DEF1`–`DEF5` objects). A mirror is exported to `data/cells.json` and
`data/defs.json` for reference.

**Practical workflow:**

1. Edit `data/cells.json` (or `data/defs.json`) — not the HTML
2. Open a PR with a one-line description of what changed and why
3. The maintainer syncs it into the HTML and rebuilds

> Yes, this means your PR isn't the final artifact yet. The build step
> (`tools/build.js`) is on the roadmap. Until then, editing the JSON is
> still the right way to propose a change — it makes the diff reviewable.

If you'd rather not deal with git at all: open an issue with the JSON object
pasted in a code block. That works too.

## Style rules (the ones that actually matter)

**Definitions.** Write the definition a textbook would print, not the explanation
a teacher would give. "A group is a set with an associative binary operation,
an identity, and inverses" — not "a group is like a dance where everyone has a partner."

**Chinese typography.** Use full-width punctuation in Chinese text. Math symbols
stay in Unicode (χ, π₁, ≅, ⊗), not LaTeX.

**No images.** Every visual must be generated by code. This is what keeps the
whole thing a single file that works offline.

---

## Code of conduct

Be useful. Correct errors directly, without softening them into vagueness, and
without making it personal. The goal is a map that is *right*, not one that is
pleasant to edit.
